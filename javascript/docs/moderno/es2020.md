# ES2020 (ES11)

*➕ Fuori dalla serie YDKJS — l'intera sezione «JavaScript moderno» raccoglie le feature aggiunte al linguaggio dopo ES2015 (dove i sei libri si fermano), verificate su [MDN](https://developer.mozilla.org/).*

L'undicesima edizione è una delle più ricche di novità di uso quotidiano. Introduce un nuovo tipo primitivo per gli interi di grandezza arbitraria (`BigInt`), due operatori che semplificano drasticamente l'accesso a strutture annidate e i valori di default (`?.` e `??`), un nuovo combinatore di Promise (`allSettled`), e uniforma l'accesso all'oggetto globale (`globalThis`).

---

## `BigInt`

`BigInt` è un **nuovo tipo primitivo** per rappresentare interi di grandezza arbitraria, oltre il limite di sicurezza di `Number` (`2^53 − 1`, come visto nel capitolo [Valori](/docs/libro4/02-valori.md)). Si crea aggiungendo il suffisso `n` a un literal intero, oppure con la funzione `BigInt()`.

```js
const grande = 9007199254740991n;   // literal BigInt
const daNumero = BigInt(42);        // 42n
typeof grande;                      // "bigint" — nuovo tipo primitivo

/* oltre il limite sicuro di Number */
9007199254740991n + 2n;             // 9007199254740993n — esatto
9007199254740991 + 2;               // 9007199254740992  — Number: impreciso!
```

Le regole importanti:

- **Non si mescolano** `BigInt` e `Number` nelle operazioni aritmetiche: `1n + 1` lancia `TypeError`. Va fatta una conversione esplicita (`1n + BigInt(1)` o `Number(1n) + 1`).
- La **divisione tronca** verso zero (sono interi): `5n / 2n` vale `2n`, non `2.5`.
- I confronti *loose* tra tipi funzionano (`1n == 1` è `true`), quelli *strict* no (`1n === 1` è `false`).
- Non esiste supporto nell'oggetto `Math`; `BigInt` è pensato per l'aritmetica intera esatta (ID a 64 bit, timestamp ad alta risoluzione, crittografia), non per i decimali.

## Optional chaining `?.`

L'operatore di optional chaining accede a una proprietà (o chiama un metodo) solo se il riferimento a sinistra **non è** `null` o `undefined`; altrimenti l'intera espressione **corto-circuita** restituendo `undefined`, senza lanciare il classico `TypeError: Cannot read properties of undefined`.

```js
const utente = { profilo: { indirizzo: { citta: "Roma" } } };

/* prima: catena di guardie difensive */
const citta = utente && utente.profilo && utente.profilo.indirizzo && utente.profilo.indirizzo.citta;

/* ora: optional chaining */
const citta2 = utente?.profilo?.indirizzo?.citta;   // "Roma"
const cap = utente?.profilo?.indirizzo?.cap;         // undefined, nessun errore
```

Esistono tre forme:

```js
obj?.prop        // accesso a proprietà
obj?.[chiave]    // accesso con chiave dinamica
obj?.metodo()    // chiamata di metodo (se metodo esiste; altrimenti undefined)
```

Da notare: il corto-circuito è **corto**, cioè si ferma all'intera espressione a valle. In `a?.b.c`, se `a` è nullish l'intera espressione è `undefined` (non prova nemmeno `.b.c`). Distingue inoltre `null`/`undefined` da altri valori: `0?.toString()` funziona (`0` non è nullish).

## Nullish coalescing `??`

Restituisce l'operando di destra **solo se** quello di sinistra è `null` o `undefined`. È il complemento naturale di `?.` e risolve un difetto classico dell'idioma `||` per i valori di default: `||` considera *default* qualsiasi valore *falsy*, inclusi `0`, `""` e `false`, che spesso sono valori legittimi.

```js
const config = { volume: 0, titolo: "" };

config.volume || 50;   // 50  — SBAGLIATO: 0 è un volume valido, ma è falsy
config.volume ?? 50;   // 0   — CORRETTO: 0 non è nullish

config.titolo || "Senza titolo";   // "Senza titolo" — "" scartata
config.titolo ?? "Senza titolo";   // ""             — "" è un valore valido
```

Per evitare ambiguità di precedenza, `??` **non può** essere combinato direttamente con `||` o `&&`: serve una parentesi esplicita.

```js
// a ?? b || c        → SyntaxError
(a ?? b) || c         // OK
```

La combinazione con l'optional chaining è l'idioma tipico per leggere un valore annidato con un default sicuro:

```js
const citta = utente?.profilo?.indirizzo?.citta ?? "Sconosciuta";
```

## `Promise.allSettled()`

Attende che **tutte** le Promise dell'array si siano concluse, indipendentemente dall'esito, e **non corto-circuita mai**. A differenza di `Promise.all()` (che rigetta appena una fallisce, vedi il capitolo [Promise](/docs/libro5/03-promises.md)), `allSettled` restituisce sempre un array di oggetti-esito, uno per ciascuna Promise, con forma `{ status: "fulfilled", value }` oppure `{ status: "rejected", reason }`.

```js
const risultati = await Promise.allSettled([
    fetch("/api/a"),   // supponiamo vada a buon fine
    fetch("/api/b"),   // supponiamo fallisca
]);

risultati;
/*
[
  { status: "fulfilled", value: Response },
  { status: "rejected",  reason: TypeError }
]
*/

/* estrarre solo i successi */
const ok = risultati
    .filter(r => r.status === "fulfilled")
    .map(r => r.value);
```

È il combinatore giusto quando servono i risultati di **tutte** le operazioni e un fallimento parziale è accettabile (per esempio, caricare più widget indipendenti di una dashboard). Con questa edizione i quattro combinatori di Promise diventano: `all` (tutti o niente), `allSettled` (tutti comunque), `race` (il primo a concludersi), a cui [ES2021](es2021.md) aggiungerà `any`.

## `globalThis`

Fornisce un riferimento **universale** all'oggetto globale, valido in ogni ambiente. Prima serviva sapere dove girava il codice: `window` nel browser, `self` nei Web Worker, `global` in Node.js — con acrobazie per scrivere codice portabile.

```js
globalThis;   // window nel browser, global in Node.js, self nei worker
```

Non è pensato per l'uso quotidiano (il codice moderno evita lo stato globale), ma è essenziale per librerie e polyfill che devono accedere all'oggetto globale in modo agnostico rispetto all'ambiente.

## `String.prototype.matchAll()`

Restituisce un **iterator** di *tutti* i match di una regex globale, ciascuno come oggetto match completo (con gruppi di cattura numerati e con nome, indice, ecc.). Risolve i limiti dei due approcci precedenti: `string.match(re_g)` con flag `g` restituisce solo le stringhe matchate (senza i gruppi), e il ciclo manuale con `re.exec()` e `lastIndex` è verboso e soggetto a errori.

```js
const testo = "2026-08 e 2027-01";
const re = /(?<anno>\d{4})-(?<mese>\d{2})/g;   // il flag g è obbligatorio

for (const m of testo.matchAll(re)) {
    console.log(m.groups.anno, m.groups.mese);
}
// 2026 08
// 2027 01

/* materializzare tutti i match in un array */
const tutti = [...testo.matchAll(re)];
```

La regex passata a `matchAll` **deve** avere il flag `g`, altrimenti viene lanciato un `TypeError`.

## Dynamic `import()`

L'operatore `import()` carica un modulo **a runtime** e restituisce una Promise del namespace del modulo. È già stato introdotto nel callout del capitolo [Organizzazione del codice](/docs/libro6/03-organizzazione.md), come forma standardizzata al posto dell'API speculativa `Reflect.Loader` che YDKJS descriveva. È qui che entra ufficialmente nel linguaggio (ES2020).

```js
/* caricamento condizionale e pigro */
button.addEventListener("click", async () => {
    const { apriEditor } = await import("./editor.js");
    apriEditor();
});
```

A differenza dell'`import` statico (che deve stare al top-level), `import()` è ammesso ovunque, valuta lo specifier a runtime, ed è la base del **code splitting** (caricare parti dell'applicazione solo quando servono).

---

## Aggiunte minori

- **`import.meta`**: un oggetto con metadati sul modulo corrente; il più usato è `import.meta.url`, l'URL del modulo, utile per risolvere risorse relative.
- **`export * as ns from "modulo"`**: re-esporta l'intero namespace di un modulo sotto un nome, come forma simmetrica dell'`import * as ns`.
- **Ordine di `for..in` standardizzato**: la specifica fissa (in gran parte) l'ordine di enumerazione di `for..in`, riducendo le differenze storiche tra i motori.

## Ripasso veloce

```js
/* BIGINT — interi di grandezza arbitraria */
9007199254740993n;        // literal con suffisso n
typeof 1n;                // "bigint"
1n + BigInt(2);           // 3n — mai mescolare con Number

/* OPTIONAL CHAINING — corto-circuito su null/undefined */
obj?.a?.b?.c;             // undefined invece di TypeError
obj?.[chiave];  obj?.metodo();

/* NULLISH COALESCING — default solo se null/undefined */
valore ?? "default";      // 0, "", false NON sono nullish
obj?.a?.b ?? "fallback";  // idioma combinato

/* PROMISE.ALLSETTLED — tutti comunque, mai corto-circuito */
await Promise.allSettled([p1, p2]);
// [{status:"fulfilled", value}, {status:"rejected", reason}]

/* GLOBALTHIS — oggetto globale universale */
globalThis;

/* MATCHALL — tutti i match con i gruppi (regex con g obbligatorio) */
[...str.matchAll(/(?<n>\d+)/g)];

/* DYNAMIC IMPORT — code splitting */
const m = await import("./modulo.js");
import.meta.url;
```

## Domande

<details>
<summary>Perché <code>??</code> è preferibile a <code>||</code> per i valori di default?</summary>

Perché `||` restituisce l'operando di destra quando quello di sinistra è *falsy*, e i valori falsy includono `0`, `""`, `false` e `NaN` — che in molti contesti sono valori **legittimi**, non "assenza di valore". Per esempio `volume || 50` sostituisce erroneamente un volume di `0` con `50`. L'operatore `??` (nullish coalescing) restituisce l'operando di destra **solo** quando quello di sinistra è `null` o `undefined`, cioè quando il valore è davvero assente. Così `volume ?? 50` preserva lo `0`. Si usa `||` quando si vuole scartare *tutti* i valori falsy, `??` quando si vuole scartare *solo* i nullish.

</details>

<details>
<summary>Cosa restituisce <code>a?.b.c</code> se <code>a</code> è <code>null</code>, e perché?</summary>

Restituisce `undefined`, senza lanciare errori e **senza** tentare di valutare `.b.c`. Questo è il comportamento di *corto-circuito* dell'optional chaining: quando l'operando a sinistra di `?.` è `null` o `undefined`, l'intera espressione che segue viene abbandonata e si restituisce `undefined`. Non è quindi equivalente a `(a?.b).c`, che invece proverebbe ad accedere a `.c` di `undefined` e lancerebbe `TypeError`. Il corto-circuito si propaga fino alla fine della catena di accessi. Va ricordato che `?.` reagisce solo a `null`/`undefined`: su valori come `0` o `""` (non nullish) l'accesso procede normalmente.

</details>

<details>
<summary>Qual è la differenza tra <code>Promise.all()</code>, <code>Promise.allSettled()</code> e <code>Promise.any()</code>?</summary>

Sono tre combinatori con politiche diverse. `Promise.all()` è un *gate* "tutto o niente": si fulfilla con l'array dei valori solo se **tutte** si fulfillano, e rigetta immediatamente appena **una** fallisce. `Promise.allSettled()` (ES2020) attende sempre **tutte** e non rigetta mai: restituisce un array di oggetti-esito `{status, value}` o `{status, reason}`, lasciando al chiamante il compito di distinguere successi e fallimenti — ideale quando i fallimenti parziali sono tollerabili. `Promise.any()` ([ES2021](es2021.md)) è l'opposto di `all`: si fulfilla con il **primo** valore fulfilled e rigetta solo se **tutte** falliscono, con un `AggregateError` che raccoglie tutte le reason. `Promise.race()` invece si conclude con il **primo** a *concludersi*, fulfillment o rejection che sia.

</details>

<details>
<summary>Perché <code>BigInt</code> e <code>Number</code> non possono essere mescolati nelle operazioni aritmetiche?</summary>

Perché hanno semantiche numeriche diverse e incompatibili, e mescolarli richiederebbe una conversione implicita che comporterebbe perdita di precisione silenziosa — esattamente il problema che `BigInt` esiste per evitare. Un `Number` è un float IEEE 754 a 64 bit con precisione intera garantita solo fino a `2^53 − 1`; un `BigInt` è un intero esatto di grandezza arbitraria. Convertire un `BigInt` grande in `Number` lo arrotonderebbe, mentre convertire un `Number` decimale in `BigInt` perderebbe la parte frazionaria. Per rendere il rischio esplicito, la specifica lancia `TypeError` su operazioni miste come `1n + 1`, obbligando lo sviluppatore a scegliere consapevolmente la conversione (`Number(x)` o `BigInt(x)`). I confronti *loose* (`==`) e relazionali (`<`, `>`) sono invece ammessi tra i due tipi, perché non producono un nuovo valore ambiguo.

</details>
