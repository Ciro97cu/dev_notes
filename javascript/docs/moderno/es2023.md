# ES2023 (ES14)

*➕ Fuori dalla serie YDKJS — l'intera sezione «JavaScript moderno» raccoglie le feature aggiunte al linguaggio dopo ES2015 (dove i sei libri si fermano), verificate su [MDN](https://developer.mozilla.org/).*

La quattordicesima edizione è compatta ma centrata su un tema importante: l'**immutabilità**. I nuovi metodi *change-by-copy* offrono le versioni non-mutanti delle operazioni che storicamente modificavano l'array sul posto, in linea con gli stili di programmazione immutabile diffusi nei framework moderni. Si aggiungono la ricerca dal fondo (`findLast`), i Symbol come chiavi delle collezioni deboli e la grammatica hashbang.

---

## `findLast()` e `findLastIndex()`

Sono i simmetrici, che partono **dal fondo**, dei metodi `find()` e `findIndex()` introdotti in ES6 (visti nel capitolo [Aggiunte alle API](/docs/libro6/06-api-additions.md)). Restituiscono rispettivamente l'ultimo elemento, e il suo indice, che soddisfa la callback, scandendo l'array da destra a sinistra.

```js
const numeri = [1, 2, 3, 4, 5, 6];

numeri.findLast(n => n % 2 === 0);      // 6  — ultimo pari
numeri.findLastIndex(n => n % 2 === 0); // 5  — suo indice

numeri.findLast(n => n > 10);           // undefined
numeri.findLastIndex(n => n > 10);      // -1
```

Prima, per cercare dal fondo bisognava invertire l'array (`[...arr].reverse().find(...)`) — costoso e con l'indice da ricalcolare. Sono disponibili anche sui `TypedArray`.

---

## Change Array by Copy: `toSorted`, `toReversed`, `toSpliced`, `with`

Storicamente `sort()`, `reverse()` e `splice()` **mutano** l'array su cui operano, e assegnare a un indice (`arr[i] = v`) modifica l'originale. Questo mal si concilia con lo stile immutabile (per esempio con lo state management di React/Redux, dove lo stato non va mutato). ES2023 aggiunge quattro metodi che restituiscono un **nuovo array**, lasciando intatto l'originale.

| Metodo mutante (esistente) | Versione a copia (ES2023) |
|---|---|
| `arr.sort(cmp)` | `arr.toSorted(cmp)` |
| `arr.reverse()` | `arr.toReversed()` |
| `arr.splice(i, del, ...items)` | `arr.toSpliced(i, del, ...items)` |
| `arr[i] = v` | `arr.with(i, v)` |

```js
const originale = [3, 1, 2];

const ordinato = originale.toSorted();     // [1, 2, 3]
originale;                                 // [3, 1, 2] — INVARIATO

const invertito = originale.toReversed();  // [2, 1, 3]
const modificato = originale.with(0, 99);  // [99, 1, 2] — originale intatto
const spliced = originale.toSpliced(1, 1); // [3, 2] — rimuove l'elemento a indice 1
```

Il vantaggio pratico: si possono concatenare trasformazioni senza mai alterare i dati di partenza, e senza il consueto `[...arr].sort()` per proteggere l'originale. `with(index, value)` in particolare è la controparte immutabile dell'assegnazione per indice, e accetta indici negativi. Tutti e quattro esistono anche sui `TypedArray`.

> [!tip]
> `toSorted()` eredita da `sort()` la stabilità garantita da [ES2019](es2019.md), ma **non** la conversione a stringa implicita quando manca il comparatore: come `sort()`, senza comparatore ordina secondo l'ordine lessicografico delle rappresentazioni stringa. Per un ordinamento numerico serve sempre `toSorted((a, b) => a - b)`.

## Symbol come chiavi di WeakMap

Fino a ES2022 le collezioni deboli (`WeakMap`, `WeakSet`, `WeakRef`, `FinalizationRegistry`) accettavano come chiavi/valori **solo oggetti**, come descritto nel capitolo [Collezioni](/docs/libro6/05-collezioni.md). ES2023 estende l'ammissibilità ai **Symbol non registrati** (cioè creati con `Symbol()`, non con `Symbol.for()`).

```js
const chiave = Symbol("meta");
const wm = new WeakMap();

wm.set(chiave, { dati: 42 });   // ora ammesso: Symbol come chiave
wm.get(chiave);                 // { dati: 42 }
```

La ragione: un Symbol non registrato è un valore **unico e non riproducibile**, quindi può essere raccolto dal GC come un oggetto — condizione necessaria per una chiave debole. I Symbol del registry globale (`Symbol.for("x")`), invece, restano **esclusi**: sono per definizione sempre raggiungibili tramite il registry, non verrebbero mai raccolti e violerebbero la semantica "debole".

## Hashbang grammar

La sequenza hashbang (o *shebang*) `#!` all'inizio della prima riga di un file è ora parte ufficiale della grammatica di script e moduli. Sui sistemi Unix indica al kernel quale interprete usare per eseguire il file direttamente.

```js
#!/usr/bin/env node

console.log("Eseguibile come programma a riga di comando");
```

Prima questa riga era supportata *de facto* da Node.js e da altri runtime, che la rimuovevano prima del parsing, ma non era nella specifica. ES2023 la standardizza: l'hashbang è consentito **solo** come primissima sequenza del file (nemmeno uno spazio prima) e viene trattato come un commento.

## Ripasso veloce

```js
/* RICERCA DAL FONDO */
[1, 2, 3, 4].findLast(n => n < 3);      // 2
[1, 2, 3, 4].findLastIndex(n => n < 3); // 1

/* CHANGE BY COPY — non mutano l'originale */
arr.toSorted(cmp);        // vs sort()   (muta)
arr.toReversed();         // vs reverse() (muta)
arr.toSpliced(i, d, ...); // vs splice()  (muta)
arr.with(i, valore);      // vs arr[i]=v  (muta)

/* SYMBOL come chiave di collezioni deboli (solo Symbol() non registrati) */
new WeakMap().set(Symbol("k"), valore);

/* HASHBANG — solo come primissima riga */
#!/usr/bin/env node
```

## Domande

<details>
<summary>Perché i metodi <em>change-by-copy</em> sono importanti per la programmazione immutabile?</summary>

Perché eliminano la mutazione accidentale dei dati condivisi. I metodi storici `sort()`, `reverse()` e `splice()`, e l'assegnazione `arr[i] = v`, modificano l'array **sul posto**: se quell'array è uno stato condiviso (per esempio lo state di un componente React, che non va mai mutato direttamente), l'operazione lo corrompe e può causare bug sottili di rendering o di reattività. Prima ci si proteggeva copiando manualmente (`[...arr].sort()`), un idioma facile da dimenticare. I metodi `toSorted`, `toReversed`, `toSpliced` e `with` restituiscono sempre un **nuovo** array lasciando intatto l'originale, rendendo le trasformazioni immutabili concise e sicure per default, e concatenabili senza effetti collaterali.

</details>

<details>
<summary>Perché i Symbol registrati con <code>Symbol.for()</code> non sono ammessi come chiavi di <code>WeakMap</code>?</summary>

Perché violerebbero la semantica "debole" della collezione. Una `WeakMap` tiene le chiavi con un riferimento debole: la voce può sparire quando la chiave non è più raggiungibile da nessun'altra parte, permettendo al GC di raccoglierla. Un Symbol creato con `Symbol()` (non registrato) è un valore unico che, come un oggetto, può diventare irraggiungibile e quindi collezionabile — condizione compatibile con una chiave debole. Un Symbol del registry globale, creato con `Symbol.for("x")`, è invece **permanentemente raggiungibile** attraverso il registry stesso: `Symbol.for("x")` restituirà sempre lo stesso Symbol, in ogni momento del programma. Non diventa mai irraggiungibile, quindi come chiave debole non verrebbe mai raccolto, rendendo priva di senso la sua presenza in una collezione debole. Per questo la specifica lo esclude.

</details>

<details>
<summary>Come si cercava l'ultimo elemento che soddisfa una condizione prima di <code>findLast()</code>?</summary>

Bisognava invertire l'array e usare `find()`/`findIndex()`: `[...arr].reverse().find(predicato)`. Questo approccio ha due difetti. Primo, l'inefficienza: crea una copia completa dell'array e la inverte, solo per cercare dal fondo. Secondo, con `findIndex` l'indice risultante è quello *nell'array invertito*, e va ricalcolato rispetto all'originale con `arr.length - 1 - indiceInvertito` — passaggio facile da sbagliare. `findLast()` e `findLastIndex()` scandiscono direttamente l'array da destra a sinistra senza copiarlo e restituiscono l'indice già riferito all'array originale, rendendo l'operazione sia più efficiente sia meno soggetta a errori.

</details>
