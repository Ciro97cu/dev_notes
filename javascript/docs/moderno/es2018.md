# ES2018 (ES9)

La nona edizione estende l'asincronia dai singoli valori agli **stream** di valori (async iteration), aggiunge il tassello mancante alle Promise (`finally`), porta spread/rest agli oggetti e rinnova profondamente le espressioni regolari, colmando lacune storiche rispetto ad altri linguaggi (lookbehind, gruppi con nome, `\p{...}`).

---

## Iterazione asincrona: `for await...of` e async generator

L'iteratore sincrono di ES6 produce valori disponibili *immediatamente*. Ma molte sorgenti reali — righe di un file, chunk di una risposta di rete, messaggi di uno stream — producono valori **nel tempo**, uno dopo l'altro, ciascuno dietro una Promise. ES2018 introduce il protocollo dell'**async iterator**: come quello sincrono ha un metodo `next()`, ma `next()` restituisce una *Promise* di `{ value, done }` invece dell'oggetto diretto. Il gancio è `Symbol.asyncIterator` (l'analogo asincrono di `Symbol.iterator`).

Il ciclo `for await...of` consuma un async iterable, attendendo ogni valore prima di procedere:

```js
async function elabora(stream) {
    for await (const chunk of stream) {
        console.log(chunk);   // attende ogni chunk, in ordine
    }
}
```

Il modo più semplice di produrre un async iterable è un **async generator**, cioè una funzione `async function*` che combina `await` (per attendere) e `yield` (per emettere):

```js
async function* contaConRitardo(n) {
    for (let i = 1; i <= n; i++) {
        await new Promise(r => setTimeout(r, 1000)); // attende 1s
        yield i;                                     // emette il valore
    }
}

for await (const v of contaConRitardo(3)) {
    console.log(v); // 1, poi 2, poi 3 — a un secondo di distanza
}
```

`for await...of` funziona anche su iterable di Promise (attende ciascuna) ed è utilizzabile solo dentro una funzione `async` (o al top-level di un modulo, da [ES2022](es2022.md)).

## `Promise.prototype.finally()`

Registra un callback che viene eseguito **in ogni caso** alla conclusione della Promise — sia in caso di fulfillment sia di rejection — senza ricevere né il valore né la reason. È l'equivalente del blocco `finally` di `try/catch`, ideale per il cleanup che deve avvenire comunque (chiudere uno spinner, rilasciare una risorsa).

```js
mostraSpinner();
fetch("/api/dati")
    .then(res => res.json())
    .then(dati => usa(dati))
    .catch(err => segnala(err))
    .finally(() => nascondiSpinner());   // sempre, in ogni caso
```

Punti chiave del comportamento: il callback di `finally()` non riceve argomenti (non deve decidere in base all'esito) e, di norma, è **trasparente** rispetto alla catena — non altera il valore o l'errore che propaga. Restituire un valore da `finally` viene ignorato; l'unica eccezione è che se `finally` **lancia** (o restituisce una Promise rejected), quel nuovo errore sovrascrive l'esito precedente, esattamente come nel `finally` di `try/catch`.

## Spread e rest sugli oggetti

Lo spread `{ ...obj }` e il rest `const { a, ...resto } = obj` sono standardizzati proprio in ES2018. Sono già illustrati nel capitolo [Oltre ES6](/docs/libro6/08-oltre-es6.md), dove il libro li trattava come proposta: si rimanda a quella spiegazione.

## Novità sulle espressioni regolari

ES2018 è l'edizione che moderna più le regex. Quattro aggiunte indipendenti.

### Named capture groups

Un gruppo di cattura può ricevere un nome con la sintassi `(?<nome>...)`, e i valori catturati diventano accessibili come proprietà di `match.groups` invece che per posizione numerica — codice molto più leggibile e robusto ai riordinamenti.

```js
const re = /(?<anno>\d{4})-(?<mese>\d{2})-(?<giorno>\d{2})/;
const m = "2026-08-02".match(re);

m.groups.anno;   // "2026"
m.groups.mese;   // "08"
m.groups.giorno; // "02"

/* backreference a un gruppo con nome: \k<nome> */
/(?<q>['"]).*?\k<q>/.test(`"testo tra virgolette"`); // true

/* riferimento nel replace: $<nome> */
"2026-08-02".replace(re, "$<giorno>/$<mese>/$<anno>"); // "02/08/2026"
```

### Lookbehind assertions

Al lookahead di ES3 (`(?=...)`, `(?!...)`) ES2018 affianca il **lookbehind**: `(?<=...)` (positivo) e `(?<!...)` (negativo) verificano ciò che *precede* la posizione corrente, senza includerlo nel match.

```js
/* prende le cifre precedute da € ma non include il simbolo */
"costo €42".match(/(?<=€)\d+/)[0];   // "42"

/* prende i numeri NON preceduti da $ */
"€42 e $99".match(/(?<!\$)\b\d+/g);  // ["42"]
```

### Flag `s` (dotAll)

Per default il metacarattere `.` non corrisponde ai terminatori di riga. Il flag `s` (*dotAll*) fa sì che `.` corrisponda **a qualsiasi** carattere, newline compreso.

```js
/inizio.fine/.test("inizio\nfine");   // false — . non copre \n
/inizio.fine/s.test("inizio\nfine");  // true  — con s, sì
```

### Unicode property escapes

Con il flag `u` diventano disponibili gli escape `\p{...}` (e la negazione `\P{...}`), che matchano caratteri in base alle loro **proprietà Unicode** — categoria generale, script, e altri attributi — invece che con classi ad hoc come `[a-z]`.

```js
/* qualsiasi lettera, in qualsiasi alfabeto */
/\p{Letter}/u.test("ω");          // true
/^\p{L}+$/u.test("Größe");        // true

/* per script specifico */
/\p{Script=Greek}/u.test("λ");    // true

/* emoji e simboli */
/\p{Emoji}/u.test("🎉");          // true
```

## Ripasso veloce

```js
/* ASYNC ITERATION */
async function* gen() { yield await fetch("/a"); yield await fetch("/b"); }
for await (const v of gen()) { /* attende ogni valore */ }
// gancio: Symbol.asyncIterator; next() → Promise<{value, done}>

/* PROMISE.FINALLY — cleanup in ogni caso, trasparente alla catena */
p.then(ok).catch(err).finally(cleanup);

/* OGGETTI: spread/rest → vedi cap. "Oltre ES6" */

/* REGEXP */
/(?<y>\d{4})-(?<m>\d{2})/         // named groups → match.groups.y
"a-b".replace(re, "$<m>")         // riferimento nel replace
/(?<=€)\d+/                       // lookbehind positivo
/(?<!\$)\d+/                      // lookbehind negativo
/a.b/s                            // flag s: . copre anche \n
/\p{Letter}/u                     // Unicode property escape (richiede u)
```

## Domande

<details>
<summary>In cosa differisce un async iterator da un iterator sincrono?</summary>

Un iterator sincrono espone `next()` che restituisce direttamente un oggetto `{ value, done }`, e il suo gancio è `Symbol.iterator`. Un async iterator espone `next()` che restituisce una **Promise** di `{ value, done }`, e il suo gancio è `Symbol.asyncIterator`. Questo permette di rappresentare sorgenti che producono valori nel tempo (rete, file, stream), dove ogni valore diventa disponibile solo dopo un'operazione asincrona. Si consuma con `for await...of` invece di `for...of`, e il modo più naturale di produrne uno è un `async function*` (async generator), che può usare `await` per attendere e `yield` per emettere. `for await...of` è utilizzabile solo dentro una funzione `async` o al top-level di un modulo.

</details>

<details>
<summary>Il callback di <code>Promise.prototype.finally()</code> può cambiare il valore che propaga nella catena?</summary>

In generale no: `finally()` è pensato per essere **trasparente**. Non riceve argomenti (né valore né reason) e il suo valore di ritorno viene ignorato — la catena continua a propagare il valore di fulfillment o l'errore che c'era prima. C'è però un'unica eccezione: se il callback di `finally` **lancia** un'eccezione, o restituisce una Promise che viene rejected, allora quel nuovo errore *sovrascrive* l'esito precedente. È lo stesso comportamento del blocco `finally` di `try/catch`: un `throw` nel `finally` prevale su ciò che stava per essere restituito.

</details>

<details>
<summary>Qual è il vantaggio dei named capture groups rispetto ai gruppi numerici?</summary>

Leggibilità e robustezza. Con i gruppi numerici si accede ai valori per posizione (`match[1]`, `match[2]`), il che rende il codice opaco (cosa contiene `match[3]`?) e fragile: aggiungere o riordinare un gruppo nella regex sposta tutti gli indici e rompe silenziosamente il codice a valle. Con i named group `(?<nome>...)` i valori sono proprietà di `match.groups` (`match.groups.anno`), quindi autodocumentati e stabili rispetto ai riordinamenti. Il nome è riutilizzabile anche come backreference (`\k<nome>`) all'interno del pattern e come riferimento (`$<nome>`) nella stringa di sostituzione di `replace()`.

</details>

<details>
<summary>Perché gli Unicode property escapes <code>\p{...}</code> richiedono il flag <code>u</code>?</summary>

Perché `\p{...}` ha significato solo in modalità Unicode: senza il flag `u`, la sequenza `\p` viene interpretata come un semplice `p` (identity escape), e la property escape non esiste. Il flag `u` attiva l'interpretazione Unicode-aware dell'intero pattern — i caratteri astral (oltre il BMP) vengono trattati come singola entità e diventano disponibili gli escape basati sulle proprietà Unicode ufficiali (`\p{Letter}`, `\p{Script=Greek}`, `\p{Emoji}`, ecc.). Questo permette di scrivere classi di caratteri semanticamente corrette per qualsiasi alfabeto, invece di approssimazioni ASCII-centriche come `[a-zA-Z]` che ignorano lettere accentate e altri script.

</details>
