# ES2021 (ES12)

*➕ Fuori dalla serie YDKJS — l'intera sezione «JavaScript moderno» raccoglie le feature aggiunte al linguaggio dopo ES2015 (dove i sei libri si fermano), verificate su [MDN](https://developer.mozilla.org/).*

La dodicesima edizione completa la famiglia dei combinatori di Promise con `Promise.any()`, aggiunge una terna di operatori di assegnamento logico, migliora la leggibilità dei literal numerici e la sostituzione nelle stringhe, e introduce due strumenti avanzati per interagire con il garbage collector (`WeakRef`, `FinalizationRegistry`).

---

## `Promise.any()` e `AggregateError`

`Promise.any()` si fulfilla con il valore della **prima** Promise dell'array che va a buon fine, ignorando i fallimenti. Rigetta soltanto se **tutte** falliscono, e in quel caso la reason è un nuovo tipo di errore, `AggregateError`, che raccoglie tutte le singole reason nella proprietà `.errors`.

```js
/* la prima risposta utile vince; i fallimenti vengono ignorati */
const primoMirror = await Promise.any([
    fetch("https://mirror-a.example/file"),
    fetch("https://mirror-b.example/file"),
    fetch("https://mirror-c.example/file"),
]);

/* se falliscono TUTTE */
try {
    await Promise.any([Promise.reject("x"), Promise.reject("y")]);
} catch (err) {
    err instanceof AggregateError;  // true
    err.errors;                     // ["x", "y"] — tutte le reason
}
```

È il complemento logico di `Promise.all()`: dove `all` è "tutti devono riuscire, uno che fallisce ferma tutto", `any` è "ne basta uno che riesce, falliscono solo se falliscono tutti". Da non confondere con `Promise.race()`, che si conclude con il primo a *concludersi* — anche se è un fallimento; `any` invece **ignora** i fallimenti e aspetta il primo successo.

## Operatori di assegnamento logico

Tre nuovi operatori combinano un operatore logico con l'assegnamento: `&&=`, `||=` e `??=`. La caratteristica cruciale è che sono **corto-circuitati**: l'assegnamento avviene *solo* quando serve, non incondizionatamente.

```js
a ||= b;   // assegna b ad a SOLO SE a è falsy       → a || (a = b)
a &&= b;   // assegna b ad a SOLO SE a è truthy       → a && (a = b)
a ??= b;   // assegna b ad a SOLO SE a è nullish      → a ?? (a = b)
```

Casi d'uso tipici:

```js
/* valore di default solo se assente (senza sovrascrivere 0, "", false) */
function config(opts) {
    opts.timeout ??= 3000;   // imposta il default solo se null/undefined
    opts.retry   ??= true;
}

/* aggiornare una proprietà solo se già presente */
utente.nome &&= utente.nome.trim();   // trim solo se nome è truthy
```

La semantica di corto-circuito è importante: `a ||= b` **non** è identico a `a = a || b`. Il primo esegue l'assegnamento (e quindi eventuali setter o side effect) *solo* quando `a` è falsy; il secondo assegna sempre. Questa differenza conta con getter/setter e con `Proxy`.

## Separatori numerici

Un underscore `_` può essere inserito tra le cifre di un literal numerico come separatore visivo, per rendere leggibili i numeri grandi. È puramente estetico: non ha alcun effetto sul valore.

```js
const miliardo = 1_000_000_000;
const byte = 0xFF_FF_FF_FF;
const grande = 1_000_000_000_000n;   // funziona anche con BigInt
const frazione = 3.141_592_653;
```

I separatori sono ammessi solo *tra* le cifre: non all'inizio o alla fine, non adiacenti al punto decimale o ai prefissi (`0x`, `0b`, `0o`), e non doppi.

## `String.prototype.replaceAll()`

Sostituisce **tutte** le occorrenze di un valore in una stringa. Colma un difetto storico di `replace()`: quando il pattern è una *stringa*, `replace()` sostituisce solo la **prima** occorrenza, e per sostituirle tutte bisognava ricorrere a una regex con flag `g`.

```js
"a-b-c-d".replace("-", "+");      // "a+b-c-d"  — solo la prima
"a-b-c-d".replaceAll("-", "+");   // "a+b+c+d"  — tutte

/* niente più regex g solo per sostituire tutto */
const bonificato = testo.replaceAll("  ", " ");
```

Accetta anche una regex, ma con un vincolo: se è una regex, **deve** avere il flag `g` (altrimenti lancia `TypeError`, perché "sostituisci tutto" con una regex non-globale sarebbe contraddittorio). Come `replace`, supporta una funzione di sostituzione e i pattern di riferimento (`$1`, `$<nome>`).

## `WeakRef` e `FinalizationRegistry`

Due strumenti avanzati per interagire con il garbage collector, da usare con parsimonia.

`WeakRef` mantiene un riferimento **debole** a un oggetto: non ne impedisce la garbage collection. Il metodo `.deref()` restituisce l'oggetto se è ancora vivo, oppure `undefined` se nel frattempo è stato raccolto.

```js
const cache = new WeakRef(oggettoCostoso);

/* più tardi... */
const obj = cache.deref();
if (obj) {
    usa(obj);           // ancora in memoria
} else {
    /* è stato raccolto: ricrearlo se serve */
}
```

`FinalizationRegistry` permette di registrare un callback di **cleanup** che *potrebbe* venire invocato dopo che un oggetto è stato raccolto dal GC.

```js
const registry = new FinalizationRegistry((valore) => {
    console.log("raccolto:", valore);   // cleanup, ad es. chiudere una risorsa
});

registry.register(oggetto, "descrizione-per-il-cleanup");
```

> [!warning]
> La documentazione ufficiale scoraggia esplicitamente l'uso di entrambi nella maggior parte dei casi. Il garbage collector è **non-deterministico**: non c'è alcuna garanzia che il callback di `FinalizationRegistry` venga mai chiamato, né su *quando*, e il comportamento varia tra i motori. Costruire logica applicativa che dipende dalla raccolta è fragile. Sono strumenti per casi specialistici (cache che non devono trattenere in memoria i propri valori, integrazione con risorse esterne), non per l'uso comune. Fonte: [MDN — WeakRef § Avoid where possible](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakRef).

## Ripasso veloce

```js
/* PROMISE.ANY — primo successo; AggregateError se falliscono tutte */
await Promise.any([p1, p2, p3]);
// catch → err instanceof AggregateError, err.errors = [...]

/* ASSEGNAMENTO LOGICO — corto-circuitato (assegna solo se serve) */
a ||= b;   // se a falsy
a &&= b;   // se a truthy
a ??= b;   // se a nullish  → idioma per i default

/* SEPARATORI NUMERICI — solo estetici */
1_000_000;  0xFF_FF;  1_000n;

/* REPLACEALL — tutte le occorrenze (regex, se usata, con g) */
"a.b.c".replaceAll(".", "/");   // "a/b/c"

/* WEAKREF / FINALIZATIONREGISTRY — avanzati, GC non-deterministico */
const ref = new WeakRef(obj);
ref.deref();   // obj | undefined
```

## Domande

<details>
<summary>Qual è la differenza tra <code>Promise.any()</code> e <code>Promise.race()</code>?</summary>

Entrambi restituiscono un risultato "il primo che...", ma con criteri opposti riguardo ai fallimenti. `Promise.race()` si conclude con la **prima Promise a concludersi**, qualunque sia l'esito: se la prima a risolversi è un rejection, `race` rigetta con quella reason. `Promise.any()` invece **ignora i rejection** e si fulfilla con il **primo successo** (fulfillment); rigetta soltanto se *tutte* le Promise falliscono, e in tal caso lo fa con un `AggregateError` che contiene l'array di tutte le reason in `.errors`. In sintesi: `race` = "il primo a finire", `any` = "il primo a riuscire". `any` è utile per pattern di ridondanza (interrogare più mirror e prendere la prima risposta valida), `race` per i timeout (correre contro una Promise che fallisce dopo N ms).

</details>

<details>
<summary>Perché <code>a ||= b</code> non è identico a <code>a = a || b</code>?</summary>

Per il **corto-circuito sull'assegnamento**. `a = a || b` valuta `a || b` e poi assegna *sempre* il risultato ad `a`, anche quando `a` era già truthy (in quel caso riassegna ad `a` il suo stesso valore). `a ||= b` invece esegue l'assegnamento **solo quando `a` è falsy**: se `a` è già truthy, non tocca affatto `a`. La differenza è osservabile quando l'assegnamento ha side effect — per esempio se `a` è una proprietà con un setter, o è intercettata da un `Proxy`: con `||=` il setter viene invocato solo nel caso in cui serva davvero scrivere, con `= a || b` verrebbe invocato sempre. Lo stesso vale per `&&=` (assegna solo se truthy) e `??=` (assegna solo se nullish).

</details>

<details>
<summary>Quando <code>replaceAll()</code> lancia un errore con una regex?</summary>

`replaceAll()` lancia `TypeError` quando gli si passa una regex **priva del flag `g`** (global). La ragione è di coerenza semantica: una regex senza `g` è concepita per trovare una singola corrispondenza, quindi chiedere di "sostituire tutte le occorrenze" con essa sarebbe contraddittorio. La specifica preferisce segnalare l'incongruenza con un errore piuttosto che comportarsi in modo ambiguo. Quando il pattern è invece una semplice **stringa**, `replaceAll` sostituisce tutte le occorrenze senza bisogno di alcuna regex — ed è proprio questo il suo vantaggio principale rispetto a `replace()`, che con un pattern-stringa sostituisce solo la prima.

</details>

<details>
<summary>Perché la documentazione scoraggia l'uso di <code>WeakRef</code> e <code>FinalizationRegistry</code>?</summary>

Perché entrambi dipendono dal comportamento del garbage collector, che è **non-deterministico** e non fa parte del contratto osservabile del linguaggio. Non c'è alcuna garanzia su *se* e *quando* un oggetto verrà raccolto: il callback di `FinalizationRegistry` potrebbe non essere mai invocato (ad esempio se il programma termina prima), potrebbe essere invocato molto dopo che l'oggetto è diventato irraggiungibile, e il momento esatto varia tra i motori e tra le versioni. Analogamente, `WeakRef.deref()` può restituire l'oggetto o `undefined` in modo imprevedibile tra una chiamata e l'altra. Costruire logica applicativa che si affida a questi tempi produce codice fragile e difficile da testare. Sono strumenti legittimi solo per casi specialistici (cache che non devono prolungare la vita dei propri valori, o cleanup di risorse esterne come ultima difesa), mai come meccanismo primario.

</details>
