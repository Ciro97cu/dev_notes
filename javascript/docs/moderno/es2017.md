# ES2017 (ES8)

*➕ Fuori dalla serie YDKJS — l'intera sezione «JavaScript moderno» raccoglie le feature aggiunte al linguaggio dopo ES2015 (dove i sei libri si fermano), verificate su [MDN](https://developer.mozilla.org/).*

L'ottava edizione dello standard consolida due filoni: da un lato completa gli strumenti di introspezione degli oggetti (`Object.values`, `Object.entries`, `Object.getOwnPropertyDescriptors`), dall'altro porta a sintassi di prima classe il pattern asincrono più atteso — `async`/`await`. Sul fronte delle prestazioni, introduce la memoria condivisa tra thread con `SharedArrayBuffer` e `Atomics`.

---

## `async` / `await`

La coppia `async`/`await` è la novità più importante dell'edizione, ma è già trattata a fondo nel capitolo [Oltre ES6](/docs/libro6/08-oltre-es6.md) come naturale evoluzione del pattern *generator + Promise + runner*. In sintesi: `async function` restituisce sempre una Promise, e `await` sospende la funzione fino alla risoluzione della Promise attesa, facendo apparire il codice asincrono come sequenziale. Si rimanda a quel capitolo per la spiegazione completa.

---

## `Object.values()` e `Object.entries()`

ES5 offriva già `Object.keys()`, che restituisce l'array delle chiavi proprie ed enumerabili di un oggetto. ES2017 aggiunge le due controparti mancanti: `Object.values()` per i valori e `Object.entries()` per le coppie `[chiave, valore]`.

```js
const salari = { anna: 3200, bruno: 2800, carla: 3500 };

Object.keys(salari);    // ["anna", "bruno", "carla"]
Object.values(salari);  // [3200, 2800, 3500]
Object.entries(salari); // [["anna", 3200], ["bruno", 2800], ["carla", 3500]]
```

L'ordine di iterazione segue le stesse regole di `Object.keys` (prima gli integer index in ordine crescente, poi le chiavi stringa in ordine di inserimento). `Object.entries()` è particolarmente comodo perché produce coppie direttamente destrutturabili in un `for..of`, e perché è l'inverso naturale di `Object.fromEntries()` (introdotto in [ES2019](es2019.md)):

```js
for (const [nome, salario] of Object.entries(salari)) {
    console.log(`${nome}: ${salario}€`);
}

/* trasformare un oggetto passando per le entries */
const aumentati = Object.fromEntries(
    Object.entries(salari).map(([nome, s]) => [nome, s * 1.05])
);
```

Entrambi considerano solo le proprietà **proprie** ed **enumerabili** con chiave stringa; le proprietà con chiave `Symbol` vengono ignorate.

## `Object.getOwnPropertyDescriptors()`

Restituisce **tutti** i property descriptor propri di un oggetto in un unico oggetto (chiave → descriptor), completando `Object.getOwnPropertyDescriptor()` (singolare, già in ES5).

```js
const sorgente = {
    get nomeCompleto() { return `${this.nome} ${this.cognome}`; },
    nome: "Ada"
};

Object.getOwnPropertyDescriptors(sorgente);
/*
{
    nomeCompleto: { get: f, set: undefined, enumerable: true, configurable: true },
    nome:         { value: "Ada", writable: true, enumerable: true, configurable: true }
}
*/
```

Il caso d'uso concreto è la **copia fedele** di un oggetto: `Object.assign()` copia i valori *invocando* getter e setter (li appiattisce in valori statici), mentre la combinazione con `getOwnPropertyDescriptors` preserva getter, setter e attributi:

```js
/* copia che preserva accessor e prototype */
const copia = Object.create(
    Object.getPrototypeOf(sorgente),
    Object.getOwnPropertyDescriptors(sorgente)
);
```

## String padding: `padStart()` e `padEnd()`

Due metodi di `String.prototype` che allungano una stringa fino a una lunghezza target, aggiungendo un riempimento rispettivamente all'inizio o alla fine. La firma è `padStart(targetLength, padString = " ")`.

```js
"5".padStart(3, "0");        // "005"
"5".padEnd(3, "0");          // "500"
"42".padStart(5);            // "   42"  (padding di default: spazio)

/* allineamento di una colonna */
["1", "23", "456"].map(s => s.padStart(4));
// ["   1", "  23", " 456"]
```

Se la stringa è già lunga almeno quanto `targetLength`, viene restituita invariata. Se il `padString` non entra esatto nello spazio rimanente, viene troncato.

## Trailing comma nei parametri e nelle chiamate

ES2017 ammette una virgola finale (*trailing comma*) anche nelle liste di parametri delle funzioni e negli argomenti delle chiamate — non solo negli array e negli object literal, dove era già consentita.

```js
function foo(
    a,
    b,   // virgola finale ammessa
) { /* ... */ }

foo(
    1,
    2,   // ammessa anche nella chiamata
);
```

Il vantaggio è pratico: aggiungere un parametro non tocca la riga precedente, così i diff di controllo di versione restano puliti (una riga aggiunta, non due modificate).

## `SharedArrayBuffer` e `Atomics`

Come visto nel capitolo [Performance](/docs/libro5/05-performance.md), i Web Worker comunicano di norma per messaggi (structured clone o Transferable), senza condividere memoria. ES2017 introduce l'eccezione: `SharedArrayBuffer` è un buffer di memoria grezza che **più agenti** (il thread principale e i worker) possono mappare contemporaneamente con le proprie view TypedArray, vedendo gli stessi byte in tempo reale.

```js
const shared = new SharedArrayBuffer(1024);   // 1 KB condiviso
const view = new Int32Array(shared);

/* il buffer può essere inviato a un worker: entrambi vedono la stessa memoria */
worker.postMessage(shared);   // NON viene copiato: è condiviso
```

La memoria condivisa reintroduce però le **race condition** a livello di istruzione, il problema che il modello single-thread eliminava. L'oggetto `Atomics` fornisce le operazioni **atomiche** (indivisibili, non interrompibili a metà) necessarie a coordinare gli accessi in sicurezza:

```js
Atomics.add(view, 0, 5);     // view[0] += 5, atomicamente
Atomics.load(view, 0);       // lettura atomica
Atomics.store(view, 0, 42);  // scrittura atomica
Atomics.compareExchange(view, 0, 42, 100); // CAS: se è 42, metti 100

/* sincronizzazione bloccante (solo nei worker, non sul thread UI) */
Atomics.wait(view, 0, 100);  // attende finché view[0] === 100
Atomics.notify(view, 0, 1);  // risveglia 1 agente in attesa
```

> [!warning|label:Oggi]
> Dopo la scoperta delle vulnerabilità **Spectre** (inizio 2018) i browser **disabilitarono** `SharedArrayBuffer`, perché la memoria condivisa ad alta risoluzione permetteva di costruire timer sfruttabili per l'attacco. Oggi è di nuovo disponibile, ma **solo in contesti "cross-origin isolated"**: la pagina deve inviare gli header HTTP `Cross-Origin-Opener-Policy: same-origin` e `Cross-Origin-Embedder-Policy: require-corp`. Senza questi header, in un contesto browser `SharedArrayBuffer` non è utilizzabile. In Node.js, invece, è sempre disponibile. Fonte: [MDN — SharedArrayBuffer § Security requirements](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer).

## Ripasso veloce

```js
/* OGGETTI: introspezione completa */
Object.values(obj);    // [val, ...]
Object.entries(obj);   // [[key, val], ...] — destrutturabile in for..of
Object.getOwnPropertyDescriptors(obj); // copia fedele di accessor e attributi

/* STRINGHE: padding */
"7".padStart(3, "0");  // "007"
"7".padEnd(3, "0");    // "700"

/* SINTASSI: trailing comma anche in parametri e chiamate */
function f(a, b,) {}

/* CONCORRENZA: memoria condivisa + operazioni atomiche */
const sab = new SharedArrayBuffer(1024);
const ta = new Int32Array(sab);
Atomics.add(ta, 0, 1);
Atomics.wait(ta, 0, 0);   // solo nei worker; richiede COOP/COEP nel browser

/* async/await → vedi cap. "Oltre ES6" */
async function main() { const x = await fetch("/api"); }
```

## Domande

<details>
<summary>Qual è la differenza tra <code>Object.assign()</code> e la copia via <code>Object.getOwnPropertyDescriptors()</code>?</summary>

`Object.assign(target, source)` copia le proprietà leggendone il **valore corrente** tramite un normale accesso: se la source ha un getter, `assign` ne invoca il getter e copia nel target il valore *risultante*, appiattendo l'accessor in un dato statico. Non copia i descriptor, quindi perde `writable`/`enumerable`/`configurable` non standard e non copia il prototype. La combinazione `Object.create(Object.getPrototypeOf(src), Object.getOwnPropertyDescriptors(src))` invece preserva getter e setter come tali, tutti gli attributi dei descriptor e il prototype — è la ricetta corretta per una copia superficiale *fedele* di un oggetto con accessor.

</details>

<details>
<summary>Perché <code>Object.entries()</code> è comodo per trasformare un oggetto?</summary>

Perché rende un oggetto processabile con i metodi degli array. Si convertono le proprietà in un array di coppie `[chiave, valore]` con `Object.entries()`, si applicano `map`/`filter`/`reduce` come su qualsiasi array, e si ricostruisce un oggetto con `Object.fromEntries()` ([ES2019](es2019.md)). Questo colma una lacuna storica: gli oggetti non hanno metodi di trasformazione propri, mentre gli array sì. Il pattern `Object.fromEntries(Object.entries(obj).map(...))` è l'equivalente per oggetti di un `arr.map(...)`.

</details>

<details>
<summary>Perché <code>SharedArrayBuffer</code> richiede l'oggetto <code>Atomics</code> mentre un normale <code>ArrayBuffer</code> no?</summary>

Un `ArrayBuffer` normale non è condiviso tra agenti: vive in un solo thread, e il modello single-thread di JavaScript garantisce che nessuna funzione venga interrotta a metà (run-to-completion). Non ci sono quindi race condition a livello di istruzione. Un `SharedArrayBuffer` è invece mappato simultaneamente da più thread, che possono leggerlo e scriverlo *nello stesso istante* su core diversi: riemerge la possibilità di letture/scritture parziali o interlacciate. `Atomics` fornisce operazioni indivisibili (`add`, `load`, `store`, `compareExchange`, `wait`, `notify`) che il processore esegue senza che nessun altro thread possa osservarne uno stato intermedio, permettendo di coordinare gli accessi senza corruzione dei dati.

</details>

<details>
<summary>Cosa succede se il <code>targetLength</code> di <code>padStart()</code> è minore della lunghezza della stringa?</summary>

Non accade nulla: la stringa viene restituita invariata. `padStart()` e `padEnd()` allungano una stringa *fino a* una lunghezza minima, ma non la accorciano mai. Se la stringa è già lunga almeno quanto `targetLength`, non viene aggiunto alcun padding. Inoltre, se il `padString` fornito non entra esattamente nello spazio rimanente, viene troncato per rispettare precisamente la lunghezza target.

</details>
