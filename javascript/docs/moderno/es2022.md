# ES2022 (ES13)

La tredicesima edizione è dominata dal completamento della sintassi delle **classi**: campi di istanza (pubblici e privati), metodi privati, campi statici e blocchi di inizializzazione statici. Le classi di ES6 (viste nel capitolo [Organizzazione del codice](/docs/libro6/03-organizzazione.md)) avevano solo costruttore e metodi; ES2022 colma il resto. Completano l'edizione `.at()`, `Object.hasOwn`, `Error.cause`, il top-level `await` e il flag RegExp `d`.

---

## Campi di classe (class fields)

Fino a ES2021 le proprietà di istanza andavano dichiarate dentro il `constructor` (`this.x = ...`). ES2022 permette di dichiararle direttamente nel corpo della classe come **campi**, con eventuale valore iniziale.

```js
class Contatore {
    valore = 0;              // campo pubblico di istanza, con default
    step = 1;

    incrementa() {
        this.valore += this.step;
    }
}
```

I campi vengono inizializzati alla creazione dell'istanza (prima del corpo del costruttore, se presente). La dichiarazione rende esplicita, in cima alla classe, la "forma" delle istanze — cosa che con l'inizializzazione sparsa nel costruttore restava implicita.

### Campi e metodi privati (`#`)

Il prefisso `#` dichiara un membro **realmente privato**: accessibile solo dall'interno della classe, invisibile e inaccessibile dall'esterno (anche via `[]` o reflection). È una privatezza *hard*, garantita dal linguaggio — diversa dalla convenzione ES precedente del prefisso `_`, che era solo un suggerimento.

```js
class ContoBancario {
    #saldo = 0;                      // campo privato
    #pin;                            // privato senza default

    constructor(pin) { this.#pin = pin; }

    deposita(importo) { this.#saldo += importo; }   // OK dall'interno
    #verificaPin(p) { return p === this.#pin; }     // metodo privato

    preleva(importo, pin) {
        if (this.#verificaPin(pin)) this.#saldo -= importo;
    }
}

const c = new ContoBancario("1234");
c.#saldo;   // SyntaxError — il campo privato non esiste fuori dalla classe
```

Anche i **metodi**, i **getter/setter** e i membri **statici** possono essere privati (`#metodo()`, `get #x()`, `static #y`). L'accesso a un membro privato inesistente è un errore di *sintassi*, non un `undefined` a runtime: la privatezza è verificata a compile time.

### Ergonomic brand checks: `#campo in oggetto`

Poiché accedere a un campo privato di un oggetto che non lo possiede lancia un errore (non restituisce `undefined`), serve un modo sicuro per *verificare* se un oggetto è un'istanza "genuina" della classe (ha il "brand"). Lo fornisce l'operatore `in` applicato a un nome privato:

```js
class Temperatura {
    #celsius;
    constructor(c) { this.#celsius = c; }

    static èTemperatura(obj) {
        return #celsius in obj;   // true solo per istanze genuine di Temperatura
    }
}

Temperatura.èTemperatura(new Temperatura(20)); // true
Temperatura.èTemperatura({ celsius: 20 });     // false — non ha il campo privato
```

### Campi statici e blocchi statici

I **campi statici** (`static x = ...`) appartengono alla classe, non alle istanze. Il **blocco statico** `static { ... }` esegue codice di inizializzazione al momento della definizione della classe — utile per logica di setup che non entra in una singola espressione (per esempio inizializzare più campi statici in relazione tra loro, o accedere a membri privati statici).

```js
class Config {
    static #istanza;             // privato statico
    static versione = "1.0";     // pubblico statico

    static {
        // eseguito una volta, alla definizione della classe
        Config.#istanza = new Config();
        console.log("Config inizializzata, v" + Config.versione);
    }
}
```

## `.at()`

Il metodo `.at(index)` legge l'elemento a un indice, con il supporto per gli **indici negativi** che contano dalla fine — cosa che la sintassi `[]` non offre. È disponibile su `Array`, `String` e i `TypedArray`.

```js
const arr = [10, 20, 30, 40];

arr.at(0);    // 10
arr.at(-1);   // 40  — ultimo elemento (prima: arr[arr.length - 1])
arr.at(-2);   // 30

"ciao".at(-1);   // "o"
```

L'indice negativo elimina il verboso `arr[arr.length - 1]` per accedere agli ultimi elementi. Fuori range restituisce `undefined`, come l'accesso `[]`.

## `Object.hasOwn()`

Sostituisce la classica `Object.prototype.hasOwnProperty.call(obj, key)` con una funzione statica più sicura e leggibile, per verificare se un oggetto ha una proprietà **propria** (non ereditata).

```js
const o = { a: 1 };

Object.hasOwn(o, "a");          // true
Object.hasOwn(o, "toString");   // false — ereditata dal prototype

/* prima, il pattern verboso e fragile: */
Object.prototype.hasOwnProperty.call(o, "a");
```

`Object.hasOwn` è più robusto di `o.hasOwnProperty("a")` perché funziona anche quando l'oggetto non eredita da `Object.prototype` (per esempio creato con `Object.create(null)`) o quando ha ridefinito `hasOwnProperty`.

## `Error.cause`

Il costruttore di `Error` (e delle sue sottoclassi) accetta ora un secondo argomento con un'opzione `cause`, per **incatenare** gli errori: un errore di alto livello può conservare l'errore originario che lo ha provocato, senza perderne lo stack.

```js
try {
    leggiConfig();
} catch (err) {
    throw new Error("Avvio fallito", { cause: err });
}

/* più a valle, si può risalire alla causa originaria */
catch (e) {
    console.error(e.message);   // "Avvio fallito"
    console.error(e.cause);     // l'errore originale di leggiConfig()
}
```

Prima si ricorreva a proprietà custom o a messaggi concatenati; `cause` standardizza il pattern.

## Top-level `await`

Nei **moduli** ES è ora possibile usare `await` direttamente al livello più esterno, senza doverlo racchiudere in una `async function`. Il modulo che lo usa diventa asincrono: i moduli che lo importano attendono che la sua valutazione sia completata.

```js
/* modulo config.js */
const risposta = await fetch("/config.json");
export const config = await risposta.json();   // await al top-level del modulo
```

È comodo per inizializzazioni asincrone dei moduli (caricare configurazione, connettersi a una risorsa, scegliere dinamicamente una dipendenza con `import()`). Vale solo nei moduli, non negli script classici.

## RegExp match indices: flag `d`

Il flag `d` (*hasIndices*) fa sì che il risultato di un match includa una proprietà `.indices` con le posizioni di **inizio e fine** di ciascun gruppo di cattura, non solo il testo. Utile per gli strumenti che devono evidenziare o rimpiazzare precisamente porzioni di testo.

```js
const re = /(?<anno>\d{4})-(?<mese>\d{2})/d;
const m = "2026-08".match(re);

m.indices[0];              // [0, 7]  — l'intero match
m.indices[1];              // [0, 4]  — primo gruppo (anno)
m.indices.groups.anno;     // [0, 4]  — per nome
```

## ⚡ Ripasso veloce

```js
/* CLASS FIELDS */
class C {
    x = 0;              // campo pubblico
    #segreto = 1;       // campo privato (hard privacy)
    #metodo() {}        // metodo privato
    static contatore = 0;   // campo statico
    static { /* init */ }   // blocco statico
    static è(o) { return #segreto in o; }  // brand check
}

/* .at() — indici negativi */
[1, 2, 3].at(-1);       // 3
"abc".at(-1);           // "c"

/* Object.hasOwn — proprietà propria, sicuro */
Object.hasOwn(obj, "k");

/* Error.cause — incatenamento errori */
throw new Error("msg", { cause: erroreOriginale });

/* top-level await (solo nei moduli) */
const dati = await fetch("/api").then(r => r.json());

/* RegExp flag d — indici dei match */
"2026".match(/\d{4}/d).indices[0];   // [0, 4]
```

## Domande

<details>
<summary>Qual è la differenza tra un campo privato <code>#x</code> e la vecchia convenzione del prefisso <code>_x</code>?</summary>

Il prefisso `_` era solo una **convenzione**: `obj._x` restava una normale proprietà pubblica, accessibile e modificabile dall'esterno, e il `_` comunicava soltanto "per favore non toccare". Il prefisso `#` introduce invece una privatezza **hard**, imposta dal linguaggio: un campo `#x` è accessibile *esclusivamente* dall'interno del corpo della classe che lo dichiara. Dall'esterno non è raggiungibile in alcun modo — né con `obj.#x`, né con `obj["#x"]`, né tramite `Object.keys`, reflection o altro — e il tentativo di accedervi fuori dalla classe è un **errore di sintassi**, rilevato a compile time. Inoltre i nomi privati non collidono mai con proprietà pubbliche o con campi privati di altre classi, anche se hanno lo stesso testo.

</details>

<details>
<summary>Perché serve l'operatore <code>#campo in oggetto</code> per il brand check?</summary>

Perché accedere a un campo privato su un oggetto che *non* lo possiede non restituisce `undefined` (come farebbe una proprietà pubblica assente), ma **lancia un errore**. Questo rende impossibile il tipico check difensivo `if (obj.#x !== undefined)`: se `obj` non è un'istanza genuina della classe, la sola valutazione di `obj.#x` fa fallire il programma. L'operatore `#campo in obj` risolve il problema fornendo un test *sicuro*: restituisce `true` se l'oggetto possiede quel campo privato (ed è quindi un'istanza autentica creata dalla classe, il suo "brand"), `false` altrimenti, senza mai lanciare. È il modo idiomatico per una classe di riconoscere le proprie istanze anche in presenza di oggetti che ne imitano la forma pubblica.

</details>

<details>
<summary>A cosa serve un blocco statico <code>static { ... }</code> se esistono già i campi statici?</summary>

Un campo statico (`static x = espressione`) inizializza un singolo valore con una singola espressione. Il blocco statico serve quando l'inizializzazione a livello di classe richiede **logica** che non entra in un'espressione: più istruzioni, un `try/catch`, un ciclo, o l'inizializzazione coordinata di più campi statici che dipendono l'uno dall'altro. Inoltre il blocco statico ha accesso ai membri **privati statici** della classe, permettendo setup che dall'esterno sarebbe impossibile (per esempio popolare una `#istanza` privata secondo il pattern singleton). Viene eseguito una sola volta, al momento della valutazione della definizione della classe, nell'ordine testuale rispetto ai campi statici.

</details>

<details>
<summary>Perché <code>Object.hasOwn(obj, k)</code> è preferibile a <code>obj.hasOwnProperty(k)</code>?</summary>

Per due motivi di robustezza. Primo: `obj.hasOwnProperty(k)` presuppone che `obj` erediti il metodo da `Object.prototype`, ma un oggetto creato con `Object.create(null)` non ha prototype e quindi non possiede `hasOwnProperty` — la chiamata lancerebbe `TypeError`. Secondo: un oggetto potrebbe aver **ridefinito** `hasOwnProperty` con una propria proprietà (magari un dato con quel nome), rompendo il metodo. Il pattern difensivo storico era `Object.prototype.hasOwnProperty.call(obj, k)`, corretto ma verboso e opaco. `Object.hasOwn(obj, k)` incapsula esattamente quel pattern in una funzione statica leggibile, che funziona su qualsiasi oggetto indipendentemente dal suo prototype o dalle sue proprietà.

</details>
